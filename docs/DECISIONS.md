# Decisions (ADR-lite)

Add one entry when a spec decision changes or a new test seam is introduced. Newest last.

## ADR-001: Temporal for orchestration
Base lists Temporal in its own stack. Durable execution gives us retries, timers, idempotent workflow ids and a visibility UI for the demo. **Fallback** if blocked by Friday midnight: Postgres-backed job queue plus advisory-lock leader election, keeping the same module boundaries.

## ADR-002: NATS for device transport
Lightweight, a single container, request/reply fits batched Commands with Acks, and partitions and delays are easy to inject. There is an in-memory implementation of the same interface for tests.

## ADR-003: Next.js dashboard with a typed API contract
Next.js (App Router) + React + TypeScript + Tailwind + Recharts, in its own container, talking directly to FastAPI (REST + SSE, with CORS for the dashboard origin).
- **Typed contract.** TypeScript types are generated from FastAPI's OpenAPI schema and checked in, so the Python/TypeScript contract can't drift silently.
- **SSE path.** The browser connects straight to FastAPI, not through Next.js rewrites, to avoid proxy buffering.
- **No network at runtime.** No runtime CDN; no Google Fonts via `next/font` (it downloads at build time). Use a local font or the system stack so the demo works on venue Wi-Fi.
- **Build early.** Build the web image in ticket 01 so `npm install` stays off the critical path.

## ADR-004: 15-minute settlement intervals
The market loop runs on 15-minute RT settlement intervals (NP6-905-CD). The 5-minute SCED LMPs are out of scope for the MVP.

## ADR-005: Two test seams
Seam A is the Scenario Report (system level). Seam B is the pure domain. No other seams without a new ADR.

## ADR-006: Trunk-based: commit straight to main
Tickets land as commits directly on `main`, with no PRs.
- **Gate.** A green local `make check` is required before every push. CI runs on each push, and a red `main` is fixed forward before anything else.
- **Closing.** The ticket's final commit carries `Closes #N`, which closes the issue when it lands on `main`.
- **Parallel sessions.** They use separate clones and `git pull --rebase` before pushing.

## ADR-007: Ticket 02's fixture is a placeholder, not a live ERCOT pull
Ticket 02 asks for "one real post-RTC+B day" of LZ_HOUSTON RT-SPP prices checked in as a fixture. The ERCOT Public API requires a subscription key (`ERCOT_API_*` in `.env`), which is optional per `CLAUDE.md` and was not supplied to this autopilot session, and ERCOT's public MIS pages do not expose an unauthenticated bulk-download endpoint for `NP6-905-CD`. Rather than park the ticket over an optional credential, `data/fixtures/rtm_spp_lz_houston_2025-12-10.csv` ships a deterministic, clearly-labeled placeholder: 96 x 15-minute intervals for `2025-12-10` (after the Dec 5, 2025 RTC+B go-live), same schema ERCOT publishes, with a realistic evening scarcity-style price shape ($11-$175/MWh). None of ticket 02's acceptance criteria require the fixture's *values* to be a live pull, only that the pipeline replays a fixture day end-to-end. Ticket 03 (ERCOT + weather data cache) owns the real ingest pipeline and replaces this file once keys are available.

## ADR-008: ERCOT is unreachable from the ticket-03 build sandbox, keyless or keyed
The spec says "the ERCOT API blocks non-US IPs," anticipating the *keyed* ERCOT Public API might be unavailable and making its use optional. During ticket 03, every ERCOT-owned host — `www.ercot.com` (the keyless MIS archives `gridstatus` scrapes), `mis.ercot.com`, `api.ercot.com` and `apiexplorer.ercot.com` (the keyed Public API and its registration portal) — returned `403 Forbidden` from an Incapsula WAF, or a TLS handshake failure, for every request tried, regardless of credentials. Open-Meteo (weather) is unaffected and works normally. This is a network-level block on the build machine's egress, not a missing-credentials situation the spec's escape hatch (`pending-credentials` / `needs-keys`) was written for — so ticket 03 extends that vocabulary: `data-audit` also reports a dataset `missing` with the real HTTP/parse error as its reason when a keyless fetch fails, rather than crashing the ingest run or silently skipping the day. The full ingest pipeline (fetchers, cache, throttle, audit) is built and unit-tested with fakes so it runs correctly the moment ERCOT is reachable (e.g. from a real US-based dev machine); this sandbox cannot verify a live ERCOT pull. The Data tab and `demo-days` are demoed today by seeding the cache from the ADR-007 fixture (`gridtwin.marketdata.cli seed-fixture-day`), tagged `source=fixture_seed` in the cache so it's never mistaken for a live pull.

**Amendment (ticket 04, Sat Sep 26):** the block was the machine's VPN, which egressed in Japan (`ipinfo.io/country` → `JP`), not ERCOT itself. On a US egress (`US`), `www.ercot.com` returns 200 and the keyless ingest works; `api.ercot.com` returns 401 without keys, as expected. A US egress is all the keyless path needs. The `fixture_seed` day is now for tests and CI only: ticket 04 replaced it in the cache with the real day. The daily `NP6-905-CD` documents only go back ~9 days, so older RT SPP comes from the yearly `NP6-785-ER` workbook (`backfill-rt-spp`, `source=ercot_historical`; see DATA.md). If an ingest returns 403 again, check `ipinfo.io/country` first.

## ADR-009: Fleet State comes from telemetry; shard dispatch returns a summary
Ticket 04 (2,000 devices, 20 shards). **Fleet State** is rebuilt each interval from the latest Heartbeat per Device (the telemetry ingester batches heartbeats into `device_telemetry` once per second). Stale or unhealthy Devices are excluded; the stale threshold is `TELEMETRY_STALE_HEARTBEATS` × one replay-minute of wall time, plus the ingester's flush interval, so batching alone can never make a live Device look stale. Acks no longer write SoC back to the ledger. At run start, `seed_fleet` resets every Shard (`control.<shard>.reset`) and writes the Heartbeats it returns straight into telemetry, so the first interval sees the whole fleet. Each `dispatch_shard` activity returns a per-shard summary (dispatched, acked, delivered MW, violations), not 100 Acks, which keeps workflow history small. A random **fault** means the Device does not act (`applied=false`, 0 MW). **Response noise** scales the setpoint but stays capped at headroom, so it can never push SoC below the Reserve Floor. A floor violation now means *discharging into* the floor; a Device that is already below the floor and holding is not a violation. The Interval Result also records `budget_ms`, `online_devices`, `shard_count` and the SoC p10/p50/p90 that the Live tab draws. The Scenario Report gains `median_dispatch_ms`, `max_shards_per_interval` and `min_online_devices`; the spec's fields are unchanged.

## ADR-010: Worker-kill chaos: controller service, mid-dispatch kills, Recovery Time
Ticket 05. The **chaos controller** is its own compose service (`chaos`, port 8001) and the only one that mounts the Docker socket (local demos only). The API forwards the dashboard's chaos buttons to it and reads the `chaos_events` log from Postgres. A worker kill is aimed, not random: the controller waits until one of the run's `dispatch_shard` activities is running (Temporal's pending activities; workers register with `identity` = compose service name) and SIGKILLs that worker, so every kill lands mid-dispatch. **Recovery Time** = kill → the interrupted interval's Interval Result is recorded. To keep it well inside a 15 s interval: `dispatch_shard` heartbeats every 0.5 s with a 2 s heartbeat timeout, short activities time out after 5 s, retries start after 200 ms, a workflow cached on the dead worker moves after a 2 s sticky-queue timeout, and workflow tasks time out after 2 s rather than Temporal's default 10 s. Before that change, one run took 10.2 s to recover because a workflow task was lost with the killed worker. **Tolerance floor:** "within tolerance" is ±5 % of the Achievable Target *or* 1 kW, whichever is larger. Acks round to 1 W per Device, so a drained fleet's watt-level targets otherwise fail on rounding dust. **Known gap, left for ticket 06:** Devices don't dedupe keys yet. A retried dispatch re-applies Commands that some Devices had already acted on before the kill, so the killed interval under-reports delivery (13.2 of 14.7 MW in the reference run) and has a Duplicate Effect. The `worker-kill` scenario therefore runs a 24-interval window: one faulted interval fits the ≥ 95 % SLO. Ticket 06's device dedupe should bring that interval back within tolerance. `make test`/`make check` skip `-m e2e`; `make test-e2e` needs `make up`. Compose host ports for Postgres and the web app can be overridden (`POSTGRES_HOST_PORT`, `WEB_HOST_PORT`) for machines where another stack already holds 5432/3000.

## ADR-011: Exactly-once effects: device-side dedupe, Batch Reply counters, ledger status
Ticket 06. **Dedupe lives on the Device** (in the Shard simulator; the verdict is the pure `screen_command`): a Device answers each Idempotency Key once and replays that same Ack on every later delivery. The answer is final even when the Device faulted, so a redelivery never turns a failed Command into a late effect and duplicates change nothing at all (the Seam A test checks delivered MW is identical to a clean run). **Expiry is judged against the Device's own clock**, the latest Market Interval it has acted in, not wall or replay time: a Command whose `expires_at` is at or before that is `expired`. That needs no clock sync between worker and simulator and makes a replayed old batch deterministic. **Superseded** = a higher `seq` already acted in the same interval. **Counters travel in the reply:** a Shard now answers a batch with a `BatchReply` (`acks`, `duplicate_deliveries`, `duplicate_effects`) instead of a bare Ack list, because under the duplicate scenario the second and replayed deliveries have no caller to ack to. A duplicate delivery = a key the Shard had already received; a duplicate effect = a Device acting on a key a second time (counted independently of the dedupe, so a regression would show). Both sum up per interval into the Interval Result (with `retried_dispatches`) and into the Scenario Report. The SLO table gains a "Duplicate effects" row (target 0). **Duplicate-commands scenario:** the chaos controller broadcasts `control.chaos.duplicates` over NATS to every simulator, which then delivers each batch twice and replays the previous batch first on 30 % of batches (seeded); it is cleared after `duration_s`. **Ledger status:** `commands.status` = issued → acked / expired (expired or superseded) / failed, set from each Ack; `GET /runs/{id}/ledger` and `make ledger RUN=<id>` summarize it per interval. **Test hook:** `InMemoryTransport.fail_after_partial_send` delivers half a batch, then raises; Temporal retries `dispatch_shard`, which rebuilds the same keys. **Schema init** is serialized with a Postgres advisory lock: with a new `ALTER TABLE`, services booting together deadlocked in `init_schema` and the telemetry service died. **ADR-010's known gap is closed:** the `worker-kill` e2e run now shows 100 % within tolerance, 600 duplicate deliveries from the retried dispatches and 0 duplicate effects.

## ADR-012: Staleness, Unresponsive Devices, Reallocation and its reserve
Ticket 07. **Unresponsive Devices re-rate the Achievable Target.** The spec defines the Achievable Target as min(plan target, headroom of non-stale Devices) at decision time. A partition that lands after an interval's telemetry was read leaves those Devices in Fleet State: they get Commands and never answer. We treat a Device that sends no Ack as stale for the rest of that interval (the missing Ack is stronger evidence than a missed Heartbeat) and re-rate the Achievable Target without it. The Interval Result keeps both figures (`planned_achievable_mw`, `achievable_mw`), and SLOs use the re-rated one. One telemetry period later the same Devices are stale through the normal Heartbeat rule. **Reallocation Reserve.** The naive Strategy plans every MW of Fleet State headroom, so every Device sits at its limit and a Shortfall has nowhere to go. The planner now sees headroom less `REALLOCATION_RESERVE_PCT` (10 %), the way a VPP holds operating reserve. This costs up to 10 % of dispatched MW in exchange for in-interval recovery. With it, the compose partition run moves 1.59 MW to the reachable Devices in one round. Set it to 0 to plan on everything. **Reallocation rounds** run in the workflow after the first dispatch while the Shortfall is outside tolerance (±5 % or 1 kW). There are at most `REALLOCATION_MAX_ROUNDS` (2), and each starts only in the first `REALLOCATION_DEADLINE_PCT` (50 %) of the interval's wall budget. Shortfall goes to Devices that acted, in proportion to their remaining headroom (pure `fleet/reallocate.py`). **A `seq+1` Setpoint is the Device's new total for the interval.** The Device delivers only the increment, capped by `max_power_kw` minus what it already delivered this interval and by its floor-limited energy. The Shard tracks MW per (Device, interval) across seqs. A property test checks that no Device exceeds its power limit or crosses its floor over seq 1 + reallocation rounds. **Staleness clock.** `get_fleet_state` judges staleness at the workflow's `now` (passed in, deterministic), not the activity's wall clock. That is wall time in compose and skipped time in the in-process runner, whose `InProcessChaos` hook stands in for the simulators' heartbeat loop: every live Device heartbeats once per interval on that clock. The in-memory transport no longer publishes Heartbeats after each batch. The in-process runner now runs at the real stale threshold (4 s at 60x) instead of 30 s. **Chaos.** `partition` and `telemetry-delay` are broadcast over NATS (`control.chaos.partition`, `control.chaos.telemetry_delay`) like duplicate-commands. Each Shard picks a seeded share of its Devices. Partitioned Devices drop Commands (no Ack) and Heartbeats. Delayed Devices' Heartbeats keep their `sent_at` and are released `delay_s` later, so with 10 s > the 4 s threshold they are stale, and "de-rating" is their exclusion from Fleet State. Chaos Scripts gain `pct`, `delay_s` and a compose-only `at_offset_s`. The partition script uses 12 s so the fault lands about 2 s before the next decision while its Devices still look online, which exercises the Unresponsive-Device path end to end.

## ADR-013: Degradation Ladder, feed validator and circuit breaker in the workflow
Ticket 08. **Where it runs.** The `read_feed` activity only does IO: it returns the raw reading, or fails non-retryably when the feed raises. The feed validator (`replay/feed.py`), the circuit breaker (`replay/breaker.py`) and the ladder (`dispatch/ladder.py`) are pure and run inside `MarketIntervalWorkflow`. Their state is one `FeedGuard` (level, clean streak, breaker, recent valid prices, cached plan). `ReplayRunWorkflow` passes it to each interval, gets it back in the child's `IntervalOutcome`, and carries it through continue-as-new. Breaker time is replay time, the interval being decided, so it is deterministic and independent of replay speed. **Cached Plan horizon.** The naive Strategy plans one interval at a time, so there is no multi-interval plan to fall back on. A good L0 plan is therefore cached for `LADDER_CACHED_PLAN_INTERVALS` (2) intervals. Ticket 09's LP planner can replace this with its real horizon. **Rungs.** L1 replays the cached target. L2 (Safe Rule) never charges: it discharges the reserve-adjusted headroom only if the last valid price is at or above the discharge threshold, and only while that price is under `LADDER_SAFE_RULE_MAX_AGE_INTERVALS` (8, 2 h) old. L3 dispatches nothing, not even 0 MW Commands. A failure drops the ladder to the best rung the carried data still supports, never above its current rung. **Recovery.** The spec says the ladder "recovers upward after N clean intervals". We jump straight back to L0 after `LADDER_RECOVER_AFTER_CLEAN` (2) consecutive clean intervals, rather than climbing one rung at a time. Until then the ladder stays down and keeps acting at its current rung, on the fresh price. N ≤ the cached-plan horizon, so a single rejected reading never reaches L2. **Breaker.** Rejected snapshots count as failures, as well as outages. After `FEED_BREAKER_FAILURES` (3) consecutive failures the feed is not called at all (`circuit-open`). After `FEED_BREAKER_COOLDOWN_INTERVALS` (2) one half-open probe goes through. **Validator.** It checks range, staleness (the row is for an earlier interval), monotonic interval starts, and outliers as a robust z-score against the last 16 valid prices. The price range is now −$500 to $5,000 instead of $0 to $5,000, because ERCOT RT prices do go negative and rejecting them would stall charging on windy nights. The outlier threshold (z > 100 with a $50 MAD floor, a band of about ±$5,000) is deliberately wide: real scarcity spikes up to the $5,000 cap must be tradable. That leaves the range check to catch the $9,999 injection; tighten `FEED_OUTLIER_Z` to make the distribution check bite. **Chaos.** Feed faults need no line to the workers. The controller writes an apply/clear row to the chaos event log, and `read_feed` checks it (`active_feed_faults`) before every read. In-process, `InProcessChaos.feed_faults` answers from the Chaos Script. **Evidence.** Each Interval Result carries `feed_status` (ok / rejected / outage / circuit-open) and `feed_detail`. The Scenario Report's `degradation_timeline` lists every level change and rejected snapshot; `degradation_events` counts them.

## ADR-014: LP planner, its price forecast, and how the backtest scores Strategies
Ticket 09. **Model.** `planner/lp.py` solves one LP (HiGHS via `scipy.optimize.linprog`) on the fleet aggregate: charge, discharge and energy per interval. It uses the device model's physics, with the whole round-trip loss taken on charge, plus power limits, capacity and the Reserve Floor. It maximizes RT value minus `PLANNER_DEGRADATION_USD_PER_MWH` ($10) per MWh discharged. A $0.01/MWh wear on charge breaks ties. **Terminal value.** Energy left at the end of the horizon is worth the forecast's median price, floored at $0. Without it the LP dumps the fleet at the end of every horizon. **Charge xor discharge.** At prices below about −$90/MWh (at 90% RTE and $10 degradation), burning energy on round-trip losses pays, so the LP charges and discharges in the same interval. One net Fleet Plan target can't do that. When the LP solution has both, we re-solve as a MILP with one binary per interval. That never happened on the cached window, but it does on random prices, and a property test covers it. **Forecast (spec: "DAM SPP baseline").** `marketdata/forecast.py` uses the cached DAM SPP for the interval's hour. The spec's daily NP4-190-CD fetch only reaches the last ~9 days, so `backfill-dam-spp` (in `make data`) fills the window from ERCOT's yearly **NP4-180-ER** historical workbook, the DAM twin of the NP6-785-ER RT backfill (DATA.md). Where there is no DAM for a day, the forecast falls back to **persistence**: the RT price at the same interval one day earlier, which is always known in time. The source is recorded (`dam_spp` / `persistence` / `mixed`). With no forecast at all, the `lp` Strategy falls back to naive and the Interval Result says `strategy=naive`. **Live.** `build_plan` is an activity (it reads the cache). It solves a 96-interval rolling horizon from the current interval and acts on the first interval only, clipped to the reserve-adjusted headroom. Fleet State now carries the fleet as one battery (capacity, energy, floor, power, capacity-weighted RTE), because the planner never sees the device list (ADR-012). `LpConfig` lives in `planner/models.py` so the workflow sandbox never imports scipy. **Audit.** Each Interval Result stores `strategy`, `forecast_source` and `plan_mw` (the whole horizon, 3 dp). Below L0 the ladder sets the target, and `strategy` is empty. The Cached Plan (ADR-013) still caches the single target, not the LP's horizon. **Backtest.** `make backtest` runs each cached post-RTC+B day separately from the configured starting SoC (50%) on the 20 MW / 78.4 MWh aggregate. Naive reacts to each interval's price. LP plans the whole day once on the forecast. The DAM is fixed for the day, so re-solving every interval would give the same plan; the backtest skips that to keep ~300 days fast. Perfect foresight is the same LP on actual RT. All three are settled with one value function, which is the LP's objective at actual prices. So perfect foresight is an upper bound on every day by construction, not by luck. The backtest checks this on the whole window, and so do Seam B tests. `$/MW-month` = value / fleet MW / (days / 30.44). The report goes to `data/cache/insights/backtest.json`, which is derived data and never committed, and `GET /insights/backtest` serves it.

## ADR-015: Scarcity-risk model on the cut line, stored out-of-sample Risk Curves, lp_risk
Ticket 10. Details and numbers are in `docs/MODEL.md`.

**Cut line.** Net-load forecasts and outages are not cached; the keyless load forecast is also latest-vintage only, so using it would leak. The model therefore uses:
- the DAM price for the target hour, and that day's DAM max;
- calendar features;
- RT history;
- today's RT − DAM error;
- the last observed Houston temperature (Open-Meteo, now ingested for the window).

It keeps the same interface as the full model.

**Label.** A target interval is a spike if its RT SPP is above the p99 of the training window. The Risk Curve covers the interval being decided plus the next 15 intervals (4 h).

**Validation.** Walk-forward by month starts at Feb 2026 and purges training rows whose target falls in the test month. December and January have no prior history, so they get leave-month-out fits. Those fits are flagged, excluded from the headline metrics, and exist only so every cached day has a curve.

**Serving.** A Replay Run replays history, so the Live tab, `build_plan` and the backtest all read the stored out-of-sample prediction for each decision time from `data/cache/risk/predictions.parquet`. They do not run the model live. As a result, workers and the API never import LightGBM; `risk/paths.py` keeps `train.py` out of their import graph.

**lp_risk.** The LP gets an optional planning-only value on stored energy (the soft holdback) and plans on DAM + p × premium. With no curve it plans as `lp`. In the backtest it re-plans hourly. It scored below `lp` on the window, and MODEL.md reports that result rather than tuning on the test period.

**Web.** The Risk Curve gets its own colour (yellow) on the Live chart and the Insights bars. Realized spikes are price-coloured markers, because red stays reserved for violations and errors.

## ADR-016: Insights: Opportunity, the headline cell, SVG exports, forecast error deferred
Ticket 11.

**Pure analyses.** `insights/analysis.py` is pure and a Seam B test covers it on the two fixture days. `insights/report.py` (`make insights`) does the IO. It reads every cached real rt_spp interval for the Settlement Point in one DuckDB scan, which takes under 1 s for 295 days. It then writes `data/cache/insights/insights.json` (served by `GET /insights/report`) and the CSVs from the same report object.

**Trading day and hours.** The trading day and the hour of day are Central time. The day median is taken over that trading day's intervals.

**Top N%** uses ⌈N% × intervals⌉ intervals, with a minimum of one.

**Headline.** The ticket's demo line names "7 PM in August". We don't hardcode a cell. The headline quotes whichever hour × month cell has the highest mean $/min. On the cached window that is 8 PM in April 2026 ($20/min mean, $105/min p95), so the headline says that.

**Downtime cost** assumes a minute of outage forfeits 1/15 of the interval's Opportunity. That is an upper-bound-style expectation, because it treats the fleet as able to capture the full excess over the day median.

**Exports are SVG, not PNG.** The ticket asks for "CSV/PNG". PNG would need a plotting dependency (matplotlib) that nothing else uses. The heatmap is already a small SVG, so we export it as `downtime_heatmap.svg`, which renders in the README on GitHub. The tab's chart is the same SVG drawn live.

**Forecast error vs price is deferred.** It needs net-load forecast history (`load_forecast_vintages`, credential-gated, plus `load_actual`). Neither is cached. The report carries `forecast_error.available=false` with the reason, and the tab shows "needs ERCOT keys", as the ticket allows. The scatter itself is not built yet, and no test covers it.

**Regime comparison.** Concentration is computed per `regime`. Pre-RTC+B rows appear as a second row only when they are cached. The heatmap and headline are post-RTC+B only.
